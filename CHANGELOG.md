# Changelog

## [Unreleased]

- **Added: `uvd_x402_sdk.interop`, the offline conformance runner of the interop specification (`interop/`).** `python -m uvd_x402_sdk.interop check [--interop DIR] [MANIFEST ...]`, also installed as `uvd-interop`, runs the schema fixtures (`interop/fixtures/cases.json`) and the vectors (`interop/vectors/`) against its reference implementation, then checks each app manifest saved to a file (`/.well-known/uvd-stack.json`) against the manifest schema and against R1.10, R3.3 and R5.5. A valid manifest fixture must pass those rules too. Exit status 0 green, 1 red, 2 could not run (a failure of the runner itself included); a broken file is red with its name, never a traceback. Nothing goes over the network: a `$ref` to another document is an error, never a download. It needs `jsonschema`, in the new `interop` extra. The wheel does not ship `interop/`: pass `--interop` with a vendored copy. `evaluate_vector()` takes an `Implementation`, so other code can run the vectors.
- **Added: conformance vectors** in `interop/vectors/`, JSON so the TypeScript SDK and the Rust crate run the same files: the IP ban of profile L9 (a 403 from the API that speaks L9 whose body has only the key `error`) with the neighbours that are not a ban (the same body from another API, the permission 403 with `message` and `timestamp`, the 429 `rate_limit_exceeded`, a 409 with only `error`, `detail`); R3.1 (no public read is signed, an MCP `tools/list` or public read tool by POST included: the operation decides, not the method; every write and every read that needs identity is); R5.9 with R3.6 and R3.7 (a retry after a lost response gets 200 `already_processed`, not 409, because each attempt carries a new nonce); and the manifest rules a schema cannot express.
- **Changed: R3.1 decides by operation, not by method.** An MCP call that lists tools or calls a read tool over public data is a public read although it travels by POST, and is not signed (R9.1, R9.7), as R7.6 already assumed. `must_sign()` / `signing_conforms()` of the runner take an optional `operation` (`"read"` / `"write"`); without it, the method decides as before.
- **Changed: the spec states the order in which an event inbox decides** (R5.9, R5.10): signature, then nonce (`409 nonce_replayed`), then the duplicate (`200 already_processed`, never a 409 for a duplicate), then `stale_sequence` for a different event. R5.9 said "never 409" while R3.7 described the 409 of a repeated nonce.
- **Changed: `publish.yml` runs `python -m pytest -q tests/interop` before it builds**, in a job of its own with read access only that the publishing job needs, so a tag whose interop contract is red is not published and the unpinned test dependencies never share a runner with the upload. The schema test moved to `tests/interop/test_schemas.py`.
- Fixed: the manifest fixture `en-migracion.json` accepted an authority (`mcp.tablero.example`) that no endpoint of its manifest serves, which R3.3 forbids and the schema cannot see. It gains its `mcp` endpoint.
- **Fixed: `fetch()` signs exactly the offer, its token and its atomic amount, and refuses a mismatch before signing.** `create_authorization()` signs the token the network registry gives `token_type` on the offer's network, whatever `asset` the offer names, and converts the price `fetch()` computed with `token_decimals` back into base units with that token's decimals. So the token or the amount signed could differ from the ones `max_amount` and the purchase policy had been checked against: when the offer's `asset` was not `token_type`'s token, when `token_decimals` differed from that token's decimals, or when the offer's amount had more digits than a `Decimal` division keeps (28). `fetch()` now compares them after the ceiling and the policy, whose refusals keep their codes and their order, and before anything is signed. An offer in another token, or an amount the price does not give back, raises `ValueError` naming both, and nothing is signed. Addresses are compared as the purchase policy compares them: hex in any case, anything else exactly. **Changed:** an offer whose `asset` is not `token_type`'s token used to be signed in `token_type`'s token; to pay it, pass the `token_type` of the offer's token. An offer that names no asset is paid in the network's USDC as before, and with the offer's own token and the registry's decimals (the default `token_decimals=6` for USDC) nothing changes. Native Hedera, which signs the offer as received, is unchanged. Tests: `tests/test_fetch_offer_amount.py` goes through `fetch()` against a mocked seller with v1 and v2 offers. With the offer's own token and the registry's decimals, the amount the policy approved, the amount signed and the amount paid are the offer's for five amounts up to 23 digits, one of them with a real signature; an address in another case, another token paid with its own `token_type`, and an offer that names no asset are paid. An offer in another token, a `token_decimals` below or above the registry's, one that rounds the amount to zero, and a 30-digit amount are refused after the policy approved the offer, with no signature and no paid request, and a refusal of the policy still comes first. In `tests/test_policy_real_path.py`, the test that pays an unlisted asset without a policy now passes that asset's `token_type`. Mutations: the check removed, a check with the caller's decimals, one that refuses only a larger amount, one that checks only v1 offers, no token comparison, and a case-sensitive token comparison each turn their cases red.

They are keyword-only constructor arguments that default to `None`. The message, `reason` and `to_dict()` are unchanged, and the spent-nonce classification does not read these bodies, so `is_spent_nonce_error()` and the integrations answer what they answered.

That includes `forward_failed`, which x402-rs 2.39.6+ lists under "Nothing was sent": up to 2.39.5 the same `503` + `Retry-After: 5` also answered a hop the lease holder received. `None` otherwise, including the rows of that table named only by an `error` token and `Retry-After` (`upstream_rpc_unavailable`, `upstream_nonce_or_mempool`, `upstream_rate_limited`, `facilitator_signer_unfunded`): up to x402-rs 2.39.5 the same answers also covered a transaction whose send answer was lost, and nothing in the answer says which version sent it. Not in `to_dict()`. `parse_facilitator_error_body()` also returns `reason` and `safe_to_retry`.

- **Added: `try_settle_payment()` returns `proof_of_payment` and `safe_to_retry`.** On success, `proof_of_payment` is the facilitator's proof as its own camelCase dict (`None` without one); on failure, `safe_to_retry` is `FacilitatorError.safe_to_retry` (`None` for any other error). The five keys it returned are unchanged.
- **Fixed: the default USD amount lost a base unit.** Without `token_decimals`, `verify_payment()` / `settle_payment()` / `process_payment()` converted the price as a binary float (`int(2.01 * 10**6)` is `2009999`): 151 of the 9,999 prices from $0.01 to $99.99 went out one base unit below the amount the payer signs. `NetworkConfig.get_token_amount()` now takes a `Decimal` (a float or a string is read through its decimal form) and multiplies in `Decimal`, and neither the client nor `create_402_response_v2()` turns the price into a float any more, so the 402 a seller advertises and the requirements of its settle keep saying the same number. `build_erc8004_payment_requirements()` also converts its `amount` in `Decimal` now; its own float conversion put the same 151 prices one base unit short. The `token_decimals` path was already exact.
- **Fixed: a seller could ask for an amount no payer can sign as written.** A payer signs a whole number of base units. `create_402_response()` wrote the v1 `amount` with `str()`, which puts a `Decimal` in exponent form: `Decimal("10.00").normalize()` went out as `"1E+1"` and `Decimal("0.0000005")` as `"5E-7"`, which a strict payer refuses before signing. It is now always a plain decimal (`"10"`, `"0.0000005"`), and the default `message` says the same number. `NetworkConfig.get_token_amount()` (which prices `create_402_response_v2()` and the requirements of `verify_payment()` / `settle_payment()` / `process_payment()`), the `token_decimals` path of those requirements and `build_erc8004_payment_requirements()` dropped digits below one base unit: `0.0000015` became 1 base unit at 6 decimals and `5E-7` a price of 0. A real digit below one base unit now raises `ValueError` before anything is emitted or sent, and so does `create_402_response()` when a chain it lists cannot carry the price (`0.0000015` with a 6-decimal USDC listed; the message names the chain and its decimals); so does a price that is negative or not a finite number. Float noise is not such a digit: a price computed by multiplying floats (`Decimal(str(35 * 0.01))` is `0.35000000000000003`) is rounded to the nearest whole number of base units when it is within `10 ** -(decimals + 6)` of it, or within `abs(price) * 2 ** -49` (the noise of a float grows with its magnitude), and the v1 body says the rounded price (`"0.35"`, where it said `"0.35000000000000003"`). Measured on `n * 0.01`, `n * 0.07` and `n * 0.10` for n up to 1,000,000: none is refused at 6 or 7 decimals and each converts to the price meant. The cost of the relative bound: a real half base unit is rounded too once the price is large enough, from about $281 million at 6 decimals and $28 million at 7. Trailing zeros are valid: `2.010` is 2010000 base units at 6 decimals. The conversion is exact at any length; it no longer rounds to the 28 digits of the `Decimal` context first. The middlewares and decorators build their 402 and their requirements through these, so they round and refuse the same prices. The dynamic-price examples (the `require_payment` and `lambda_handler` docstrings, the README and `examples/lambda_example.py`) multiplied floats, `Decimal(str(items * 0.10))`; they now multiply in `Decimal`, `Decimal(items) * Decimal("0.10")`. Unchanged: a price that `str()` already wrote as a plain decimal with at most the token's decimals gives the same v1 body and the same base units, which covers every cent price from $0.01 to $99.99; native Hedera keeps its own check, at most 6 decimals, float noise included. Tests: `tests/test_exact_amount.py` runs eight price shapes at 6 and 7 decimals through each of these paths (11 of those 16 v1 bodies were in a form a strict payer refuses), every cent price and `n * 0.01` / `0.07` / `0.10` through the v1 body (n up to 10,000) and `get_token_amount()` (n up to 100,000), `lambda_handler` with the docstring's price function, and mutations: `str()` back in the v1 body, its exactness check removed, truncation back in any conversion, no tolerance, no relative bound, or a relative bound of `2 ** -30`, each turns its cases red.
- **Added: `X402Config.max_timeout_seconds`** (default `60`), the `maxTimeoutSeconds` of the requirements the client sends on `/verify` and `/settle`, fixed at 60 until now. A value that is not a positive integer raises `ValueError` at construction. Native Hedera keeps its 180.
- **Added: `X402Client(http_client=...)`**, the `httpx.Client` every facilitator call of the client goes through, and the requests of `fetch()` too, the paid one included, unless `fetch()` gets an `http_client` of its own. `close()` never closes a client passed in. With `event_hooks={"response": [hook]}` it is the public way to see the facilitator's raw answers; the hook calls `response.read()` first. The SDK sets its own timeout on `/verify`, `/settle` and its timeout fallback, `/accepts` and the `/supported` of route validation; `get_version()`, `get_supported()`, `get_blacklist()`, `health_check()` and the other GETs use the timeout of the client passed in.
- Tests: `tests/test_settle_extras.py` checks each of the above through `settle_payment()` / `try_settle_payment()` / `verify_payment()` over an injected `httpx.MockTransport` that serves answers recorded from x402-rs 2.40.0's own response code (`tests/fixtures/facilitator-settle-2.40.0/`, with the patch that records them again), and every cent price from $0.01 to $99.99 through `get_token_amount()`.

## [0.90.1] - 2026-09-23

- **Fixed: the middlewares and decorators answered `402` over a payment that may have moved.** A `402` tells the buyer to sign a new payment. The integrations (FastAPI `FastAPIX402`, `X402Depends`, `fastapi_require_payment`, `X402Middleware`; Flask `FlaskX402`, `flask_require_payment`; Django `DjangoX402Middleware`, `django_require_payment`, `X402PaymentView`; Lambda `LambdaX402.process_or_require`, `lambda_handler`; `require_payment`) sent one, or `400` in `require_payment`, for every failure that was neither a receipt-rail conflict nor transient. That included `502 settlement_unconfirmed`, where the facilitator broadcast the transaction and got no receipt, so it may be mined. They now answer:
  - **`500`** for a failure that names a transaction and is not transient (`502 settlement_unconfirmed`, any other `5xx` with a hash) and for any other `5xx` with `retryable: false`. The body adds `transaction` and `paymentId` at the top level when the facilitator sent them, its `reason`, `retryable: false`, `safeToReplay: false`, and a `message` telling the buyer not to sign another payment and to check the transaction first. No `Retry-After`. This is the TypeScript SDK's answer to `settlement_unconfirmed`.
  - **`409`** for an authorization the facilitator says was already used (`is_spent_nonce_error`), with `spentNonceEvidence` (`"structured"` or `"wording"`), the code as `reason` when a code said so, and `retryable: false`. This includes one answer that was `503`: a transient failure that also reads as spent, such as `503 idempotency_cache_corrupt`. A resend of it in a new handling carries a new key.
  - **`500`** for a `4xx` from `/settle` after `/verify` accepted the same payload: the opaque `400 contract_call_failed (ref: …)` of an EVM revert and `400 internal_error (ref: …)`, which is how x402-rs reports a nonce that Stellar, Algorand, NEAR or Sui already saw. With the same payload and signature just verified, neither is a bad signature, and the TypeScript SDK answers every settle failure it may not retry with `500`. The settle `4xx`s the facilitator sends before running anything stay a rejection: `403`, `Invalid request` and the other parse failures, `invalid_address`, `clock_error`, `reserved_idempotency_key`, `invalid_receipt_context`, `receipt_*`.
  - The receipt, when the facilitator sent one, travels in `PAYMENT-RESPONSE` on all of them.
- **Fixed: a settle mined and reverted lost its transaction.** A `/settle` `200 success: false` that names a `transaction` now raises `PaymentSettlementError` with `tx_hash` set (`try_settle_payment()` returns it), and the integrations answer `500` with the `transaction`, as the TypeScript SDK does.
- **Fixed: a settle rejected by the facilitator's re-validation could not be parsed.** x402-rs answers it in the verify's shape, `200 {"isValid": false, "invalidReason": …}`, and `settle_payment()` / `process_payment()` raised pydantic's `ValidationError`, which no integration caught. It is now a `PaymentSettlementError` with `reason` set to the `invalidReason`: a rejection, `402` (`400` in `require_payment`).
- **Added: `FacilitatorError.operation`**, `"verify"` or `"settle"` when the client raised it from that call, otherwise `None`. A keyword-only constructor argument that defaults to `None`, not included in `to_dict()`.
- Unchanged: the order starts with the receipt rail's conflicts (`409`, or `503` in flight), and a `202 settlement_in_progress` stays `503` + `Retry-After` even when it names a transaction. `is_transient_error()`, its anti-double-settle guard and the settle retry policy are unchanged: the SDK re-sends none of these. A rejection keeps its answer: an invalid signature or insufficient funds is still `402` (`400` in `require_payment`), on `/verify` and on the settle's re-validation. So are the opaque `400` tokens on `/verify`: x402-rs reports a used authorization and an invalid signature the same way there (`contract_call_failed` on EVM, `internal_error` on Stellar, Algorand, NEAR and Sui).
- Tests: `tests/test_integrations_undelivered.py` runs every middleware and decorator against a facilitator over a real socket for each case. It checks that every `500` and `409` tells the buyer not to sign another payment, and has mutations: without each new branch, its case gets the old answer. In `tests/test_integrations_replay.py`, a bare resend on a network without receipts, refused at settle, is now `500` instead of the `402` it was pinned to.
- Docs: the README's seller section and "check in this order" example follow the integrations' order.

## [0.89.0] - 2026-09-23

Changes what a seller sends and answers. Read before upgrading.

- **Changed: one purchase binding per payment handling, on by default.** `X402Config.send_idempotency_key` defaults to `True` again. A handling of a payment (a `process_payment()` call, or a `settle_payment()` call with its retries and timeout fallback) sends ONE `Idempotency-Key` on `/verify`, `/settle` and the fallback's resend. The key is random (`new_idempotency_key()`, `x402-<64 hex>`, the shape the TypeScript SDK uses) unless the call passes `idempotency_key` (new, on all four methods) or `idempotency_scope`. The SDK never sends a key derived from the `X-PAYMENT` alone: whoever holds the payment can recompute such a key, and a facilitator with durable receipts (x402-rs 2.39.0) refuses to treat possession of the payment as a binding. The facilitator gives an admitted payment's answer back only to the binding that admitted it, so a seller whose settle timed out now recovers its own answer through the fallback.
- **Changed: `/verify` carries the same key as `/settle`.** `derive_idempotency_key(payload, op, scope)` returns the settle key for both operations: `x402-settle-…`, the value earlier releases already sent on `/settle`, so a purchase settled before the upgrade keeps its key. 0.83.0 to 0.88.0 sent `x402-verify-…` on `/verify`. The receipt rail does not bind that key, so the verify of a retried purchase answered `authorization_already_settled`. A derived key is a binding only while its scope is a secret of the seller.
- **Added: a replay the handling did not admit is refused.** A handling with no binding of its own (a fresh key, no `X-UVD-Purchase`) can receive `Idempotent-Replayed: true` before any of its own attempts could have admitted the payment. It then raises `PaymentSettlementError` with reason `authorization_already_settled` (`authorization_in_flight` for a `202`), carrying the receipt. Facilitators before 2.39.0 did not tie the replay to the binding; the SDK refuses it either way. A replay answering the handling's own timed-out or failed attempt is returned.
- **Added: the receipt rail's refusals, classified.** `admitted_authorization_code(exc)` names `authorization_already_settled`, `authorization_in_flight` and `receipt_request_conflict`, read from a `/settle` 409 or a `/verify` `invalidReason`; they are also exported as constants and `ADMITTED_AUTHORIZATION_CODES`. `payment_conflict_response(exc)` returns `(status, body, headers)`: `409` for settled and conflicting authorizations, `503` + `Retry-After` while in flight (the mapping the TypeScript SDK uses), and the receipt in `PAYMENT-RESPONSE`. Settled and conflicting authorizations read as spent (`is_spent_nonce_error`) and final. An authorization in flight is transient (`is_transient_error`), and `FacilitatorError.retryable` is true for it. A `202 settlement_in_progress` is transient, and the `retry=True` policy retries it under the same key.
- **Changed: the timeout fallback raises the facilitator's refusal.** A resend answered with one of those `409`s raises that `FacilitatorError` instead of a `TimeoutError`: resending the same request without the binding never gets the success back, and a timeout invited exactly that. With the key off, that 409 is probably the seller's own payment, but nothing proves it. Reconcile `receipt.settlement` before delivering.
- **Changed: the timeout fallback waits for a settle still in flight.** When the resend under the handling's own binding gets `202 settlement_in_progress` (the timed-out settle was admitted and is moving), the fallback asks again (same request, same key) for up to `SETTLE_IN_FLIGHT_POLL_SECONDS` (30), pausing as the facilitator says (`Retry-After` or the receipt's `retry.afterSeconds`, at most 5 s). The same request ends in its settle, delivered once. Past the budget it raises that `202` (transient, with the pending receipt) instead of a `TimeoutError`.
- **Added: `idempotent_replayed`** on `SettleResponse` and `PaymentResult`, read from the `Idempotent-Replayed` header and never from the body. **Added: `idempotency_key`** on `VerifyResponse`, `SettleResponse` and `PaymentResult`, excluded from `model_dump()` so it never reaches the buyer in `PAYMENT-RESPONSE`.
- **Changed: middlewares and decorators** (FastAPI `FastAPIX402`, `X402Depends`, `fastapi_require_payment`, `X402Middleware`; Flask `FlaskX402`, `flask_require_payment`; Django `DjangoX402Middleware`, `django_require_payment`, `X402PaymentView`; Lambda `LambdaX402`, `lambda_handler`; `require_payment`) answer those refusals with `409`, or `503` + `Retry-After` while in flight, and never deliver on them. They also answer every failure without a verdict with `503` + `Retry-After` and the facilitator's `reason` (`settlement_in_progress` for its `202`): a timeout, a settle still in flight past the fallback's budget, `503 idempotency_store_unavailable` / `receipt_store_unavailable`, another retryable `5xx`, a `429`. The buyer presents the same `X-PAYMENT` later and never signs another one. Before, Flask, Django, Lambda and `require_payment` answered those with `402` (or `400`), and FastAPI with `402` for a timeout or `503` without `Retry-After`. Rejections keep their previous answer.
- **Upgrading, networks without receipts:** their answers are unchanged, except for the key now being on. A keyed settle that the facilitator cannot check against its idempotency store gets `503 idempotency_store_unavailable` and does not settle, where a call without a key used to settle. That is no verdict: `is_transient_error` is true, and the SDK's integrations answer 503 + `Retry-After` so the buyer presents the same credential again. `send_idempotency_key=False` sends no key, as 0.88.0 did by default.
- **Removed:** the once-per-process warning for a keyed call without a scope; such a call now carries a fresh key. **Exported** `transient_503_response` from the package root; the README already imported it from there.
- Tests: doubles of three facilitators over real sockets (2.39.0 receipts, 2.36.0 to 2.38.0 receipts, no receipts, in `tests/receipt_rail.py`). They cover every middleware and decorator (including a settle that outlives its timeout and a facilitator store that cannot be read), plus mutation checks showing that without the guard a replayed settle is delivered. CI now installs the `fastapi`, `flask` and `django` extras, so the integration tests run there instead of being skipped. The 0.88.0 FastAPI receipt test failed in CI's resolution for lack of `fastapi`.
- Docs: EURC on Arc mainnet is confirmed with funded payments through the public facilitator (x402 v1 and v2, 2026-09-22, hashes in `docs/networks/arc.md`); Arc testnet funded acceptance stays pending. Remove three stale notes that still said EURC was absent from Arc (`CLAUDE.md`, the `networks` docstring, the README `get_networks_by_token` example output); `tests/test_readme_eurc_networks.py` pins that printed output to the registry. No runtime change.
